# Стенд сравнения распознавателей — спека

Дата: 2026-08-28. Разбор поля, из которого это выросло —
`2026-08-28-utterance-segmentation-and-speakers-research.md`.

## Зачем

Сейчас выбрать движок или способ нарезки нечем. `stt-probe` отвечает на
два вопроса про **один** движок — «распознаёт ли вообще» и «сколько стоит
по времени», — и прямо оговаривает, что качество на наших встречах не
судит: эталона нет, а сверять расшифровку с расшифровкой другого движка
значит сверять догадку саму с собой.

Стенд закрывает ровно эту дыру: одни и те же записи, несколько
движков и способов нарезки, **эталон**, и числа, по которым решение
принимается, а не обсуждается.

## Что это не

- **Не часть приложения.** Отдельный крейт, как остальные приборы.
- **Не замена `stt-probe`.** Тот отвечает на «работает ли движок вообще» и
  остаётся входным билетом: движок, не прошедший его, в стенд не едет.
- **Не тест.** Стенд печатает числа; проходит или нет — решает человек.
  Исключение — контроли самого стенда (ниже), они падают.

## Устройство

### Крейт

`rust/crates/bench`, пакет `meetingraft-bench`, бинарь `meetingraft-bench`.
В `apps/macos` не попадает никак. Подкоманды:

| Подкоманда | Где гоняется | Что делает |
|---|---|---|
| `export` | Мак | встреча из данных приложения → случай на диске |
| `run` | Linux и Мак | один прогон: (движок × нарезка × смещение) по случаю |
| `judge` | Мак (там Ollama) | слепое парное сравнение двух прогонов |
| `report` | где угодно | сводная таблица по каталогу `out/` |

### Формат случая

Стенд читает **каталог случаев**, а не базу приложения. Это не удобство:
данных приложения на Linux-машине нет вовсе, и зависимость от них означала
бы стенд, который здесь не запускается.

```
<bench-root>/
  cases/<case-id>/
    mic.wav            # 16 кГц, моно, s16 — формат живого пути (ADR-005)
    system.wav         # тот же формат; может отсутствовать
    meta.toml
    reference.txt      # эталон текста, если есть
    speakers.csv       # правда о говорящих, если есть
  out/<run-id>/
    run.json           # машиночитаемый результат
    segments.txt       # расшифровка с временем, для чтения глазами
    report.md
```

`meta.toml`:

```toml
case = "2026-08-14-standup"
language = "ru"                  # ADR-003: ru | en | es
speakers_expected = 3            # известное число людей; 0 — неизвестно
source = "meetingraft:1BF7AEAB"  # откуда взято
channel_clock_unified = true     # Epic 25; у старых записей false
reference_kind = "typed"         # typed | edited-draft | none
reference_covers_ms = [0, 180000]  # какой отрезок покрыт эталоном
notes = "созвон через наушники, трое, один по громкой связи"
```

**`reference_kind` обязателен и несёт смысл.** `typed` — напечатано с
нуля. `edited-draft` — правленный черновик движка, и такой эталон
**систематически льстит** тому движку, с которого черновик взят. WER на
нём читается с оговоркой, и отчёт эту оговорку печатает сам, а не
надеется на память читателя.

`reference_covers_ms` — потому что эталон почти всегда покрывает кусок, а
не всю встречу. WER считается **только по этому отрезку**, и сегменты вне
его в счёт не идут.

`speakers.csv` — `start_ms,end_ms,speaker` — правда о том, кто когда
говорил. Источник: локальная запись Zoom отдельной дорожкой на участника.

### Оси сравнения

| Ось | Значения | Откуда берётся |
|---|---|---|
| движок | `gigaam`, `parakeet`, `tone`, `whisper` | `stt`, за фичами |
| нарезка | `windows30`, `vad`, `diarize` | `bench`, `stt::vad`, `diarize` |
| смещение | `none`, `hotwords` | конфиг sherpa + глоссарий |

Прогон именуется по тройке: `gigaam+vad+none`. `whisper` собирается только
на Маке; `tone` — потоковый и стоит особняком (см. ниже).

### Как устроена нарезка

Три способа дают **одинаковый на вид** результат — список сегментов с
временем и текстом, — но приходят к нему по-разному:

- **`windows30`** — то, что делает сегодня `GigaamBatchTranscriber`:
  окна по тридцать секунд, один сегмент на окно. Он в стенде **как база
  сравнения**, а не как кандидат.
- **`vad`** — `VoiceActivityDetector` (Silero) режет запись на отрезки
  речи, каждый идёт в движок отдельно. Границы попадают в тишину, шов на
  стыке окон исчезает, тишина в движок не подаётся вовсе.
- **`diarize`** — `OfflineSpeakerDiarization` (pyannote seg 3.0 + CAM++)
  даёт отрезки с меткой голоса; каждый идёт в движок отдельно, метка
  едет с сегментом. Спикер известен по построению, а не вычисляется
  перекрытием.

Ограничение по длине отрезка обязательно у всех трёх: отрезок длиннее
30 секунд режется дальше, иначе `vad` на непрерывной речи выродится в
`windows30` без окон.

### Потоковый движок стоит особняком

`tone` (T-one) — `OnlineRecognizer`, а не `OfflineRecognizer`: звук
подаётся чанками, границы реплик даёт эндпойнтинг самого движка, оси
«нарезка» у него нет. В таблице он участвует по тексту и времени, но
колонки нарезки у него свои. Смешивать его с офлайновыми в одной колонке
нельзя — это разные вопросы.

## Метрики

### По тексту

- **WER** и **CER** против эталона, только внутри `reference_covers_ms`.
  Нормализация одна на всех: регистр, пунктуация, `ё`→`е`, числа
  словами оставляются как есть. Реализация переезжает из
  `stt-probe/src/wer.rs` в общее место — **две реализации одной метрики
  разойдутся**, вопрос только когда.
- **Доля пустых сегментов** и **число слов** — для контроля, что движок
  не молчит.

### По нарезке

- число сегментов, медиана и квантили длины;
- доля времени записи, покрытая сегментами;
- **доля границ, попавших в паузу** — граница считается попавшей, если в
  окне ±200 мс вокруг неё VAD речи не видит. Это прямая мера того, режем
  ли мы по речи или по часам.

### По говорящим

**cpWER** там, где есть `speakers.csv`: расшифровка каждого говорящего
склеивается по правде и по гипотезе, WER считается при том сопоставлении
меток, которое даёт минимум. Ни WER, ни DER на вопрос «правильное ли
слово попало правильному человеку» не отвечают.

### По цене

- миллисекунд на секунду аудио, **раздельно** на нарезку и на модель;
- пиковая RSS процесса — на машине с 5 ГБ это не педантизм.

## Судья

### Что делает

Слепое парное сравнение. Два прогона по одному случаю режутся по времени
на сопоставимые отрезки (по умолчанию 60 с), судье подаётся пара текстов
без имён движков, порядок сторон рандомизируется зерном прогона. Ответ
строго структурированный: победитель (`A` | `B` | `tie`) и причина одной
фразой.

Транспорт — существующий `llm_http`; модель локальная (Ollama на Маке).
Наружу расшифровки не уходят: это свойство продукта, а не настройка.

### Три контроля, без которых вывод судьи ничего не значит

Идут **в каждом** прогоне судьи, вперемешку с настоящими парами, и их
доля печатается в отчёте:

1. **A против A.** Один и тот же текст обеими сторонами. Правильный ответ
   — `tie`. Уверенный победитель означает, что судья выбирает позицию, а
   не текст, и весь прогон недействителен.
2. **Испорченный против исходного.** Слова внутри отрезка перемешаны
   зерном. Судья обязан выбрать исходный. Не выбрал — он слеп, и его
   мнение о двух приличных расшифровках тем более ничего не стоит.
3. **Доля отказов.** Судья, у которого нет права сказать `tie`, всегда
   называет победителя. Доля `tie` на настоящих парах печатается рядом:
   ноль — подозрительно.

Пороги: на контроле 1 доля `tie` ≥ 0.8, на контроле 2 доля правильных
ответов ≥ 0.9. Не выполнено — стенд печатает отказ и **не показывает
результаты сравнения вовсе**. Показать их с оговоркой хуже: оговорку
прочтут один раз, а число запомнят.

### Правило, которое важнее всех чисел судьи

**Судья мерит связность, а не верность.** Он не слышал звук. Гладкая
выдумка выиграет у корявой правды, и это не дефект промпта, а свойство
задачи.

Поэтому: где есть эталон, **решает WER**. Судья — для отрезков, где
эталона нет, и для объяснения, *чем* одна расшифровка хуже другой. При
расхождении судьи и WER в отчёте печатается расхождение, а не среднее.

## Эталон

Три источника, и они отвечают на разные вопросы:

| Источник | На что отвечает | Чего не даёт |
|---|---|---|
| Публичный корпус (Golos, Common Voice ru) | исправен ли **стенд** | ничего про наш домен: это чтение, а не разговор |
| Свои 3 минуты, напечатанные с нуля | качество на нашем домене | дорого, поэтому коротко |
| Дорожки Zoom по участникам | кто говорил (cpWER) | ничего про текст |

Публичный корпус — **заведомо положительный случай прибора**, и он
обязателен: если WER на чтении высокий, стенд подаёт движку не тот звук,
и до наших встреч дело не доходит. Это то же правило, по которому
`count-audio-taps.swift` однажды соврал нулём.

## Контроли самого стенда

Помимо судейских. Эти **падают**, а не печатаются:

1. **Шум вместо речи** — WER обязан уехать вверх у каждого движка
   (`stt-probe` это уже умеет, переносим правило).
2. **Пустой вход** — ноль сегментов, а не один пустой на каждое окно.
3. **Публичный корпус** — WER ниже порога, иначе стенд подаёт не тот звук.
4. **Перестановка случаев** — результат по случаю не зависит от порядка
   прогона других случаев (ловит утечку состояния между прогонами).

## Отчёт

`run.json` — машиночитаемо, одна запись на прогон. `report.md` — сводная
таблица: строка `(case, engine, segmentation, biasing)`, колонки — метрики
выше. Оговорки печатаются в самой таблице, а не сноской: `edited-draft`
помечает ячейку WER, отсутствие эталона — прочерк, а не ноль.

## Порядок работ

1. Каркас: формат случая, чтение WAV, отчёт — на моке, без единой модели.
2. `export` с Мака.
3. Метрики: WER/CER в общее место, метрики нарезки, cpWER.
4. Ось нарезки для GigaAM: `windows30` / `vad` / `diarize`.
5. `parakeet`: закачка, движок за фичей, в стенд.
6. `tone`: потоковый путь.
7. `hotwords` + `modified_beam_search`.
8. Судья с тремя контролями.
9. Прогон, разбор, числа в беклог.

Задачи 4–7 независимы между собой; 8 не имеет смысла раньше 4.

## Чего эта спека сознательно не делает

- **Не назначает порогов качества движкам.** Стенд их меряет; какой WER
  считать достаточным — решение после чисел, а не до.
- **Не трогает живой путь.** Ни одна задача здесь не меняет
  `SttPipeline`. Подстановка другого движка в живой путь — отдельная
  работа после чисел, и её нельзя делать одновременно с их получением.
- **Не обещает, что стенд переживёт эти замеры.** Это инструмент под
  задачу. Если после разбора он не нужен — он удаляется, и это нормальный
  исход, а не потеря.
