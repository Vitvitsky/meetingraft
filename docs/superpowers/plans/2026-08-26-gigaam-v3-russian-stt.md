# GigaAM v3 как русский движок распознавания — план работ

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** прогнать GigaAM v3 на нашем звуке и получить два числа — WER на
записи с известным текстом и время прохода на секунду аудио, — не трогая
ни живой путь, ни интерфейс.

**Architecture:** движок — `stt::gigaam` за фичей `gigaam`
(`sherpa-onnx` → `OfflineRecognizer`, `model_type = "nemo_transducer"`),
реализующий существующий `BatchTranscriber`. Поиск моделей на диске и
переход от посимвольных токенов к словам — чистые функции **без** фичи,
проверяемые обычным `cargo test`. Судит движок прибор `stt-probe`.

**Tech Stack:** Rust (крейты `domain`, `stt`, новый `stt-probe`),
sherpa-onnx 1.13. Swift не участвует. **Всё это собирается и гоняется на
Linux** — в отличие от `whisper.rs`.

Спека: `docs/superpowers/specs/2026-08-26-gigaam-v3-russian-stt-design.md`.

## Global Constraints

- Комментарии и документация в коде — **по-русски**; сообщения коммитов и
  тела PR — **по-английски** (`CLAUDE.md`).
- **Полный `cargo test` по workspace не влезает в память Linux-машины.**
  Гонять по крейтам: `cd rust && cargo test -p meetingraft-stt`.
- Имена пакетов с префиксом: крейт `stt` — пакет `meetingraft-stt`.
- Перед коммитом: `cargo fmt --check && cargo clippy --all-targets -- -D warnings`.
- **Фича `gigaam` выключена по умолчанию.** `build.rs` крейта
  `sherpa-onnx` ходит в сеть; обычная сборка не качает ничего.
- **Ни строки в живом пути.** `window.rs`, `local_agreement.rs`,
  `pacing.rs`, `noise_gate.rs`, `whisper.rs` в этом плане не меняются.
- **Ни одного нового `Ffi*`-типа.** Границу UniFFI работа не переходит.
- **Прибор не судит движок без записи с известным текстом** и без
  отрицательного контроля. Оба случая — часть самопроверки, а не
  украшение.
- Ветка: `feat/gigaam-v3-russian-stt`.

### Task 4: Движок за фичей

**Files:**
- Modify: `rust/crates/stt/Cargo.toml` (фича `gigaam`, зависимость)
- Create: `rust/crates/stt/src/gigaam.rs`
- Modify: `rust/crates/stt/src/lib.rs`

**Interfaces:**
- Produces: `GigaamBatchTranscriber` (реализует `BatchTranscriber`),
  `GigaamRecognizer::transcribe(pcm, rate) -> GigaamHypothesis`.
- Consumes: `resolve_gigaam_models` (Task 2),
  `words_from_char_tokens` (Task 3), `normalize_segments` (есть).

- [x] **Step 1: Фича и зависимость**

По образцу `diarize`: `gigaam = ["dep:sherpa-onnx"]`, `default = []`,
комментарий про сеть в `build.rs`.

- [x] **Step 2: Открытие движка**

`OfflineRecognizerConfig` с transducer-путями и
`model_type = "nemo_transducer"`. Отказ открыть — `ModelLoad` с текстом,
а не паника: у нас модель качается руками и может быть недокачана.

- [x] **Step 3: Один проход**

`create_stream` → `accept_waveform` (f32, 16 kHz) → `decode` →
`get_result`. Из результата: текст и слова с временем через
`words_from_char_tokens`. Отсутствие `timestamps` — законный случай
(поле `Option`), тогда слова идут без времени и сегмент получает границы
целого куска.

- [x] **Step 4: `BatchTranscriber` поверх прохода**

Окно 30 с, как у `whisper_batch`, — и число взято не из свойств GigaAM, а
ради одинаковости: сравнивать два движка проще, когда режут они
одинаково. Час встречи одним куском дал бы непредсказуемую память на
энкодере и ни одной точки отмены.

Один сегмент на окно. Делить речь на реплики движок не умеет, а делать
это по паузам между словами — отдельное решение, и принимать его вслепую
не за чем. Записать это в комментарии честно: привязка спикеров по
сегментам (Phase 11) с этим движком грубее, чем с Whisper.

- [x] **Step 5: `cargo build -p meetingraft-stt --features gigaam`**

### Task 5: WER, проверенный на самом себе

**Files:**
- Create: `rust/crates/stt-probe/Cargo.toml`
- Create: `rust/crates/stt-probe/src/wer.rs`
- Modify: `rust/Cargo.toml` (member)

**Interfaces:**
- Produces: `wer(reference: &str, hypothesis: &str) -> WerReport`
  (расстояние Левенштейна по словам: замены, вставки, пропуски).

Без фичи: считалка — чистая функция, и проверяется она обычным тестом.

- [x] **Step 1: Написать падающие тесты**

Три случая, и третий — тот, ради которого всё:

- совпадение → 0.0;
- одно слово из пяти заменено → 0.2 (число выводится из фикстуры: одна
  ошибка на длину эталона, а не вписано);
- **эталон против заведомо чужого текста → не меньше 1.0.** Без этого
  случая считалка, всегда возвращающая ноль, проходит первые два.

Нормализация перед сравнением: регистр, знаки препинания, `ё` → `е`.
Whisper ставит пунктуацию, GigaAM-transducer не ставит — сравнивать их
без снятия пунктуации значит мерить не то.

- [x] **Step 2: Реализовать**

### Task 6: Прибор

**Files:**
- Create: `rust/crates/stt-probe/src/main.rs`
- Reuse: `rust/crates/diarize-probe/src/wav.rs` через `#[path]` — **тем же
  файлом, а не копией**: формат один, и вторая реализация означала бы две
  правды об одном

**Interfaces:**
- Consumes: `stt::GigaamBatchTranscriber`, `wer` (Task 5).
- Produces: печать на stdout, код возврата.

- [x] **Step 1: Самопроверка — два заведомых случая**

Первым делом, до всякого настоящего звука:

1. **Положительный:** `check/example.wav` против `check/example.txt`.
   WER обязан быть ниже 0.2. Порог — граница «движок распознаёт эту
   запись», а не оценка качества модели; выше него дальше не идём.
2. **Отрицательный:** тот же эталон против прохода по **шуму** той же
   длины. WER обязан быть не ниже 0.8.

Провал любого — прибор печатает, чего не хватает, и выходит с ненулевым
кодом. Собрано без фичи — то же самое: «собрано без `--features gigaam`,
распознавать нечем».

Третьим — **тайм-коды слов**: непусты, не идут назад, не выходят за
длину записи. Отдельной проверкой, потому что теряются они отдельно от
текста: при расхождении длин токенов и тайм-кодов движок отдаёт верный
текст без времени, WER остаётся нулевым, и пакетный проход молча кладёт
всё окно одним сегментом с границами окна.

- [x] **Step 2: Время**

На обоих проходах замерить и напечатать **время на секунду аудио**.
Абсолютное число тут CPU-шное и на Мак не переносится; смысл в том, чтобы
оно вообще было снято одним и тем же способом на обеих машинах.

- [x] **Step 3: Настоящий звук**

Аргументом — путь к WAV (16 kHz mono). Прибор печатает расшифровку и
время; **вердикта о качестве не выносит**: эталона на наши встречи нет, и
выдумывать его — это и есть «сверять догадку сама с собой». Судит
человек, читая рядом с whisper'овской расшифровкой.

Если рядом с WAV лежит `.txt` с тем же именем — считается и WER.

## Что показал прогон

Linux, 4 ядра, `--release`, 4 потока onnxruntime (`num_threads` по
умолчанию), 2026-08-26. Контрольная запись — 11.3 с, эталон из Пушкина.

| Что | Число |
|---|---|
| WER на контрольной записи | **0.000** (26 слов, ни одной правки) |
| WER на шуме той же длины и громкости | **1.000** (одно слово: «да») |
| Время на речи | **96–102 мс на секунду аудио** (три прогона) |
| Время на шуме | **85–92 мс на секунду аудио** |
| Тайм-коды | 26 слов, монотонны, последнее на 10 880 мс из 11 290 |

То есть на CPU без всякого ускорителя движок идёт **вдесятеро быстрее
реального времени**. Речь дороже шума на десяток миллисекунд, и это не
шум замера: RNNT гоняет декодер с joiner'ом на каждый выданный символ, а
на шуме он не выдаёт почти ничего.

**Про шум сказано с поправкой, и поправка стоила утверждения.** В первой
редакции здесь стояло «на шуме молчит, а не выдумывает — в отличие от
Whisper с его `hallucination.rs`», и снято это было на шуме, который
генератор делал **тише записи на 5 дБ**: у равномерного шума с размахом
`a` собственный RMS равен `a/√3`, а размахом ставился сам RMS записи.
После починки — шум ровно той громкости, что заявлена, — движок выдал на
одиннадцати секундах слово «да».

Это по-прежнему несравнимо с титрами Whisper, и WER остаётся 1.000. Но
«молчит» — неправда, и держать её в тексте нельзя: на неё сослались бы,
решая, нужен ли этому движку свой отсев галлюцинаций.

### Отрицательные контроли на самом движке

Зелёный прибор проверяется тем, что он краснеет. Возвращали дефект по
одному и смотрели:

| Что сломали | Что стало |
|---|---|
| `feat_config.feature_dim` = 80 вместо 64 | **ничего не изменилось** |
| то же поле = 13 (заведомая чушь) | **ничего не изменилось** |
| PCM приглушён в 100 раз | **ничего не изменилось**, WER 0.000 |
| заявленная частота 32 кГц вместо 16 | расшифровка пуста, WER 1.000, прибор красный |
| `words_from_tokens` вместо `words_from_char_tokens` | **WER 0.000**, но «слов с временем 1, а в тексте 26» — прибор красный |

Первые две строки — про **нашу ошибку в понимании, а не про модель**.
Настройка размерности признаков стояла в коде с уверенным комментарием
(«умолчание 80 даст правдоподобный мусор»), и прогон её опроверг:
параметры признаков sherpa-onnx берёт из метаданных ONNX. Строка убрана —
настройка, которая ничего не делает, но выглядит важной, создаёт ложную
уверенность.

Третья строка полезна отдельно: тихий микрофон этот движок не ломает
(NeMo нормализует признаки). Четвёртая — то, ради чего контроли и
ставились: прибор способен покраснеть.

Пятая появилась после разбора кода и показывает **дефект, невидимый по
WER вовсе**: подмена сборщика слов склеивает фразу в одно слово, а текст
приезжает из `result.text` и остаётся верным. Первая версия проверки
тайм-кодов (непусты, монотонны, не длиннее записи) на таком входе
проходила: список `[10880]` удовлетворяет всем трём условиям. Проверка
сверяет число слов с текстом — иначе она не может сработать, а значит не
нужна.

### Чего этот прогон не говорит

- **Ничего о наших встречах.** Контрольная запись — чистая студийная
  начитка стихов. Ни перебиваний, ни терминов, ни двух каналов.
- **Ничего о Маке.** Сотня миллисекунд на секунду — это CPU этой машины.
  На Маке число снимается тем же прибором (`docs/mac-verification.md`).
- **Ничего в сравнении с Whisper.** Whisper на Linux не собран, и
  сравнивать два движка надо на одной машине и одной записи.
