# Phase 8 — System audio capture (ADR-004 wiring)

Детальный план фазы. Основание: `docs/product-ux-review-2026-08-03.md` §3.6.
Фаза доводит до конца решение ADR-004: приложение начинает записывать и
распознавать обе стороны разговора, а не только микрофон.

Правила фазы — из `AGENTS.md`: AVFoundation и Core Audio не выходят за
Swift-слой, выравнивание потоков живёт в Rust (прямое требование ADR-004),
TDD на логику ядра, Conventional Commits с русским subject. Новые строки
UI — сразу через `String(localized:)` (английский базовый).

## Исходное состояние

- `SystemAudioCapture.prepare()`
  (`apps/macos/Sources/Audio/SystemAudioCapture.swift:11-15`) безусловно
  ставит `isAvailable = false`; tap не создаётся никогда.
- `ingest_audio_chunk` (`rust/crates/ffi/src/lib.rs:1361`) отдаёт в STT
  только `FfiAudioChannel::Mic`; системный канал попал бы в manifest, но не
  в распознавание.
- `domain::CaptionEvent` (`rust/crates/domain/src/caption.rs:12`) не имеет
  поля канала — атрибутировать событие нечем.
- `LiveCaptionPipeline` (`rust/crates/stt/src/window.rs:20`) держит ровно
  один движок.
- `Info.plist` уже объявляет `NSAudioCaptureUsageDescription`
  (`apps/macos/project.yml:41`) — TCC-строка на месте.

## Ключевое решение фазы: микс для live, раздельные каналы на диске

ADR-004 требует держать каналы раздельными end-to-end и микшировать только
там, где потребителю явно нужен микс. Для live-распознавания микс нужен
именно потребителю, и вот почему альтернатива не проходит: два независимых
`LiveCaptionPipeline` означают две загруженные модели. На `large-v3`
(~1.5 ГБ) это ~3 ГБ резидентной памяти и удвоенный CPU в реальном времени —
на 8-гигабайтном Apple Silicon это неприемлемо, а бюджет латентности из
`architecture.md` («partial ≤ 2.0 s») не выдержит.

Решение: **один движок на выровненном миксе + атрибуция по доминирующему
каналу**. Канал определяется по соотношению RMS в окне сегмента с
гистерезисом; одновременная речь двоих — редкий случай, и при нём событие
достаётся громче звучащему. На диске каналы остаются раздельными (storage
уже так и делает), поэтому Phase 10 сможет гонять их по отдельности, где
время не ограничено, и получить точную атрибуцию без эвристики.

Это новое решение, а не переформулировка ADR-004, — оформляется как
**ADR-009** в T9.

## Exit criteria

- На реальном звонке в Zoom и в Meet в браузере запись и субтитры содержат
  обе стороны.
- Каналы остаются раздельными в manifest; на диске два набора чанков.
- Событие субтитра несёт канал; в UI видно, кто говорит.
- Отказ в разрешении на системный звук даёт понятное состояние с переходом
  в System Settings, а не молчаливый mic-only.
- Бюджет латентности Phase 4 не деградировал при двух активных каналах.

## T1 — тайминг чанка от счётчика кадров, а не от часов — **код готов, не проверен**

Реализовано на ветке `feat/phase-8-system-audio`, но **Swift-тесты не
запускались**: на машине разработки (Linux VPS) нет ни Swift-тулчейна, ни
Xcode. Перед продолжением фазы нужен прогон
`xcodebuild -project MeetingRaft.xcodeproj -scheme MeetingRaft test` на
Mac. До этого задача считается незакрытой.


`AudioCaptureCoordinator.ingest` (`AudioCaptureCoordinator.swift:128`)
берёт `Date()` один раз и присваивает **одно и то же** `timestampMs` всем
чанкам, которые вернул pipeline за этот вызов. Пока чанк почти всегда один,
это незаметно; для выравнивания двух каналов это фатально — метки
перестают быть монотонными и не соответствуют реальному положению звука.

- `AudioChunkPipeline.push` возвращает `[(data: Data, startFrame: UInt64)]`;
  внутренний счётчик кадров на канал, `reset()` его обнуляет.
- Координатор считает `timestampMs = startFrame * 1000 / targetSampleRate`
  для каждого чанка отдельно. Часы больше не участвуют.
- Тесты `AudioChunkPipelineTests`: смещения монотонны и не пересекаются
  через серию `push`; неполный хвост не выдаётся; `reset` возвращает
  счётчик к нулю.

Коммит: `fix: смещение чанка от счётчика кадров вместо системных часов`.

## T2 — переиспользуемая конвертация формата

Даунмикс «hardware format → 16 kHz mono Float32» сейчас заперт внутри
`MicrophoneCapture.convert` (`MicrophoneCapture.swift:55-78`), включая
неочевидную деталь про однократную отдачу буфера конвертеру. Tap отдаёт
48 kHz стерео и нуждается ровно в том же.

- `apps/macos/Sources/Audio/PCMDownmixer.swift`: тип с
  `init?(from: AVAudioFormat)` и `convert(_ buffer:) -> [Float]`.
- `MicrophoneCapture` переходит на него без изменения поведения.
- Тесты `PCMDownmixerTests`: стерео → моно (длина вдвое меньше входной);
  48 kHz → 16 kHz даёт ожидаемое число кадров ±допуск; пустой буфер даёт
  пустой массив.

Коммит: `refactor: общий даунмикс PCM для mic и system tap`.

## T3 — протокол захвата и фейки для тестов

Реальный tap не покрыть юнит-тестами, поэтому координатор должен
тестироваться на подменах.

- `protocol AudioTapping: AnyObject { var isAvailable: Bool { get }; func
  start(onSamples: @escaping ([Float]) -> Void) throws; func stop() }`.
- `MicrophoneCapture` и `SystemAudioCapture` его реализуют;
  `AudioCaptureCoordinator.init` принимает обе зависимости с дефолтами.
- Тесты `AudioCaptureCoordinatorTests`: сэмплы обоих каналов доходят до
  `ingestAudioChunk` с правильным `FfiAudioChannel`; недоступный системный
  канал не мешает записи с микрофона; ошибка старта микрофона откатывает
  сессию (текущее поведение фиксируется тестом).

Коммит: `refactor: протокол AudioTapping и внедрение зависимостей в координатор`.

## T4 — реальный process tap

Ядро фазы. API — Core Audio process taps (macOS 14.2+), как выбрано в
ADR-004; ScreenCaptureKit сознательно не используется.

- `CATapDescription(stereoGlobalTapButExcludeProcesses: [])` →
  `AudioHardwareCreateProcessTap`.
- Приватное aggregate-устройство поверх tap:
  `kAudioAggregateDeviceTapListKey`, `kAudioAggregateDeviceIsPrivateKey`,
  `kAudioAggregateDeviceMainSubDeviceKey` = UID текущего устройства вывода.
- `AudioDeviceCreateIOProcIDWithBlock` → буферы → `PCMDownmixer` →
  `onSamples`.
- Teardown строго в обратном порядке: IOProc → aggregate → tap. `stop()`
  идемпотентен; двойной вызов не должен ронять `AudioHardwareDestroy*`.
- Смена устройства вывода во время встречи (наушники воткнули) —
  подписка на `kAudioHardwarePropertyDefaultOutputDevice` и пересборка
  aggregate. Если это окажется дорого — вынести в backlog и явно
  задокументировать деградацию, но не молча.
- Ошибки различаются по смыслу: нет разрешения / API недоступен /
  устройство вывода не найдено. `isAvailable` перестаёт быть константой.

Автотестов нет по природе задачи — приёмка ручным чек-листом (ниже).

Коммит: `feat: Core Audio process tap для системного звука`.

## T6 — выравнивание каналов в Rust — **сделано**

`cargo test -p meetingraft-session` — 15 тестов зелёные (было 5), clippy и
fmt чистые. Появились два уточнения к исходному замыслу:
`set_system_expected(false)` по умолчанию (пока tap не запущен, слот не
должен простаивать допуск впустую) и `flush()` для остановки записи.


Отвечает на открытый вопрос: сейчас в Rust нет ничего, что принимало бы два
канала одновременно. ADR-004 отдаёт выравнивание session engine — туда и
кладём.

- `rust/crates/session/src/mixer.rs`, `ChannelMixer`:
  - `push(channel: AudioChannel, pcm: &[i16], timestamp_ms: u64)`;
  - слоты по длительности чанка (100 мс, как `AudioChunkPipeline`);
  - `drain() -> Vec<MixedFrame>`, где
    `MixedFrame { pcm: Vec<i16>, dominant: AudioChannel }`;
  - слот отдаётся, когда пришли оба канала **или** истёк допуск ожидания
    (недостающий канал заполняется тишиной) — иначе отсутствующий
    системный канал заблокировал бы ленту навсегда;
  - микс с насыщением (`saturating_add` на i32 с клампом в i16), без
    деления пополам: деление на два глушит монолог вдвое;
  - `dominant` по отношению RMS каналов с гистерезисом — порог плюс запас,
    чтобы атрибуция не дребезжала на границе;
  - опоздавший чанк в уже отданный слот отбрасывается и считается в
    счётчик, доступный для диагностики.
- Тесты: только mic → passthrough и `dominant == Mic`; оба канала, system
  громче → `System`; дырка в системном канале заполняется тишиной и не
  задерживает выдачу; опоздавший чанк не нарушает порядок слотов;
  переключение доминирования не дребезжит на равных амплитудах.

Коммит: `feat: выравнивание и микширование каналов в session engine`.

## T7 — канал в событии субтитра

- Миграция (шаг 2): `ALTER TABLE caption_events ADD COLUMN channel TEXT NOT
  NULL DEFAULT 'mic'` — существующие записи корректно считаются микрофонными.
- `domain::CaptionEvent` получает `channel: AudioChannel`.
- `LiveCaptionPipeline` копит гистограмму доминирования между выдачами
  событий и ставит мажоритарный канал на `Partial`/`Final` при emit;
  гистограмма сбрасывается после каждого `Final`.
- `ingest_audio_chunk` перестаёт фильтровать по `Mic`: оба канала идут в
  `ChannelMixer`, микс — в `LiveCaptionPipeline`.
- `FfiCaptionEvent` получает `channel: String`.
- Тесты: серия кадров с доминированием system даёт событие с каналом
  System; смена доминирования внутри сегмента отдаёт мажоритарный;
  сохранение и чтение из storage сохраняет канал.

Коммит: `feat: канал в событии субтитра от захвата до UniFFI`.

## Ручная приёмка

Автотестами не покрывается; прогнать перед закрытием фазы:

1. Zoom, десктопное приложение — слышно обе стороны в записи, субтитры
   идут по обоим.
2. Google Meet во вкладке браузера — то же.
3. Наушники подключены и отключены во время встречи — запись не рвётся.
4. Разрешение на системный звук отклонено — приложение работает mic-only и
   явно об этом говорит с переходом в настройки.
5. Музыка в фоне попадает в системный канал (известная плата за глобальный
   tap, ADR-004) — проверить, что это не ломает атрибуцию монолога.
6. Замер бюджета латентности из `architecture.md` при двух активных
   каналах.
