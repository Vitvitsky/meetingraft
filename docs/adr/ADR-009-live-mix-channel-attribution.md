# ADR-009: Live — один движок на миксе каналов с атрибуцией говорящего

## Status
Accepted

## Context
ADR-004 требует держать каналы захвата раздельными end-to-end и
микшировать только там, где потребителю явно нужен микс: канал `mic` —
это пользователь, канал `system` — остальные участники. Разделение
каналов даёт бесплатную атрибуцию «я / они» на звонках один на один и
чистый вход для post-call диаризации.

Live-распознавание при этом — потребитель, которому нужен именно один
поток: субтитры показываются одной хронологической лентой, а движок STT
держит внутреннее состояние сегмента (VAD-окно, контекст декодирования)
на поток.

Нужно решить, как совместить требование раздельности с одним движком.

## Options considered

1. **Два независимых `LiveCaptionPipeline`, по одному на канал.**
   Атрибуция точная и без эвристик. Но это две загруженные модели: на
   `large-v3-turbo` (~1.5 ГБ квантованной) — около 3 ГБ резидентной
   памяти и удвоенный CPU в реальном времени. На 8-гигабайтном Apple
   Silicon это неприемлемо, а бюджет латентности из `architecture.md`
   (partial ≤ 2.0 s) не выдерживается.
2. **Один движок на миксе, атрибуция по доминирующему каналу.**
   Ресурсы как у текущего mic-only пути. Атрибуция эвристическая, но
   одновременная речь двоих редка, а при ней событие достаётся тому, кто
   звучал громче в большинстве кадров сегмента.
3. **Один движок только на миксе, без атрибуции.** Дешевле всего, но
   лента «кто что сказал» не строится, и Epic 9 теряет дешёвую половину.

## Decision
Для live-пути: **один `SttEngine` на выровненном миксе плюс атрибуция по
доминирующему каналу**.

- `session::ChannelMixer` собирает чанки обоих каналов в слоты по метке
  времени (100 мс, совпадает с чанком захвата) и отдаёт
  `MixedFrame { pcm, dominant, timestamp_ms }`.
- Слот отдаётся, когда пришли все ожидаемые каналы либо истёк допуск
  ожидания; недостающий канал заполняется тишиной. Без допуска
  отсутствующий системный поток заблокировал бы ленту навсегда.
- Пока tap не запущен, системный канал не ожидается: иначе каждый слот
  простаивал бы допуск впустую и терял ~200 мс латентности на пустом
  месте.
- Микс — сумма с клампом, не среднее: деление пополам глушило бы монолог
  вдвое.
- `dominant` определяется по отношению RMS каналов с гистерезисом, чтобы
  атрибуция не дребезжала на близких уровнях.
- `LiveCaptionPipeline` копит, сколько кадров с последнего события пришло
  с каждого канала, и ставит мажоритарный канал на выданные события;
  счётчики сбрасываются после `Final`, чтобы перевес не наследовался
  следующим сегментом.
- `domain::CaptionEvent` несёт `channel`; он сохраняется в
  `caption_events` и доходит до Swift через `FfiCaptionEvent.channel`.

**Раздельность каналов ADR-004 сохраняется на диске:** `audio_manifest`
по-прежнему хранит два независимых набора PCM-чанков. Микс существует
только в live-пути и никуда не записывается.

## Consequences
### Positive
- Ресурсы live-пути не растут при включении системного звука.
- Пользователь видит, кто говорит, без диаризации и без ML.
- Post-call (Phase 10) получает нетронутые раздельные каналы и может
  обработать их по отдельности, где время не ограничено, — там атрибуция
  будет точной, а не эвристической.

### Trade-offs
- При одновременной речи двоих сегмент достаётся более громкому; вторая
  реплика атрибутируется неверно.
- Атрибуция гранулярна по сегменту, а не по слову: если внутри одного
  сегмента говорящий сменился, событие получит один канал.
- Гистерезис вносит задержку смены доминанта на границе — сознательный
  размен на устойчивость подписи.
- Точная атрибуция откладывается до post-call; live остаётся оценкой.
