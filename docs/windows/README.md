# С чего начать — навигация по репозиторию

Для разработчика, который берётся за Windows-версию и видит проект впервые. Порядок чтения имеет значение: документы ниже идут так, чтобы каждый следующий опирался на предыдущий.

## За полчаса

**1. [Описание задачи](../windows-client-brief.md)** — что за продукт, что надо сделать, десять клиентских сценариев с критериями провала, границы и порядок приёмки. Начинать отсюда.

**2. [ADR-001](../adr/ADR-001-native-first.md)** — почему приложение нативное, а логика в Rust. Одна страница, объясняет форму проекта.

**3. [ADR-004](../adr/ADR-004-audio-capture.md)** — захват двух дорожек звука. Написан про macOS, но читать целиком: там разобрано, что рассматривали и отвергли — виртуальные драйверы, захват экрана, бота в звонке. Половина вопросов, которые возникнут у вас, там уже закрыта.

## Прежде чем писать код

**4. [Контракт платформенного слоя](platform-contract.md)** — что ваш код обязан отдавать ядру: формат звука, метки времени, раздельность каналов, корень данных. Ядро это не проверяет, нарушения проявятся как разъехавшиеся дорожки.

**5. [Как оболочка разговаривает с ядром](core-interaction.md)** — взаимодействие построено на опросе, опрос двигает состояние сессии, всё ядро под одним замком, а подача звука внутри замка синхронно считает распознавание. Три вещи, которых не видно из сигнатур.

## Когда дойдёт до конкретики

**[Архитектура и схемы](../architecture-and-install.md)** — диаграммы слоёв, что в каком крейте лежит. Установочная часть macOS-специфична, схемы общие.

**[Бюджеты и контракты](../architecture.md)** — числовые требования к задержке живых субтитров, разделение Live и Final. Раздел про бюджеты входит в приёмку.

**[Словарь терминов](../naming.md)** — что в этом проекте значат «Live», «Final», «сегмент», «чанк», «канал». Короткий; если встретите термин, которого там нет, — дополните.

**Остальные ADR** (`docs/adr/`) — по мере надобности. Самые полезные для вас: ADR-005 (распознавание и почему 16 кГц), ADR-006 (что и как хранится локально), ADR-009 и ADR-012 (принадлежность реплик говорящим — то, ради чего каналы держат раздельно).

## Что читать не надо

**`docs/backlog.md`, `docs/roadmap.md`** — планы по macOS-версии. Полезны для понимания, куда движется продукт, но к вашей работе прямого отношения не имеют и местами устарели.

**`docs/superpowers/`** — рабочие спеки и планы по отдельным эпикам ядра. Внутренняя кухня.

**`docs/ui-redesign-macos-2026-08-03.md`, `docs/product-ux-review-2026-08-03.md`** — разбор интерфейса macOS. Второй документ упоминает Windows и утверждает, что его делать не надо: это решение изменилось, формулировка устарела.

## Где что лежит в коде

| Путь | Что там |
|---|---|
| `rust/crates/` | Ядро. Девять крейтов, ~13 900 строк. Переиспользуется целиком |
| `rust/crates/ffi/src/lib.rs` | Граница: 74 метода, которые зовёт оболочка |
| `rust/crates/domain/` | Типы предметной области |
| `rust/crates/storage/` | SQLite, схема в `migrations.rs` |
| `rust/crates/stt/` | Распознавание, whisper.cpp |
| `apps/macos/Sources/Audio/` | **Образец платформенного слоя.** Ваш аналог под Windows |
| `apps/macos/Sources/` | Остальная оболочка macOS — как ориентир, чего ждёт человек от экранов |
| `backend/` | Необязательный сервер для пост-обработки. К записи и субтитрам отношения не имеет |

## Сборка

Как собирается macOS-версия — `docs/architecture-and-install.md`, раздел 2. Аналога под Windows нет: чем собирать ядро, как генерировать биндинги и какой ускоритель брать для распознавания — открытые вопросы, и ответы на них станут частью вашего предложения.

Проверка ядра на своей машине:

```
cd rust && cargo test -p meetingraft-domain -p meetingraft-storage
```

Полный прогон по всему workspace требует много памяти — гоняйте по крейтам.

## Правила, которые действуют и на вас

`AGENTS.md` в корне: границы архитектуры, критерии готовности работы, команды линтеров. Раздел **Done criteria** — то, по чему принимается любая работа в этом репозитории.

Отдельно: **решения фиксируются в ADR**. Выбор механизма захвата звука под Windows и выбор стека оболочки — это решения, и они должны осесть в `docs/adr/` по образцу существующих: что выбрано, что рассмотрено и отвергнуто, какой ценой. Через полгода решение без записанного обоснования неотличимо от случайности.
