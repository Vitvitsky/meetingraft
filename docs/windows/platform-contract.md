# Контракт платформенного слоя

Что оболочка обязана дать ядру, чтобы оно работало. Всё описанное здесь ядро не проверяет и проверить не может — нарушения проявятся как разъехавшиеся дорожки или пустой транскрипт, а не как ошибка.

Документ выведен из работающей macOS-реализации: `apps/macos/Sources/Audio/`. Если что-то разойдётся с кодом — прав код, а документ надо поправить.

## Звук

Единственная точка входа:

```rust
ingest_audio_chunk(
    channel: FfiAudioChannel,   // Mic | System
    pcm: Vec<u8>,
    sample_rate: u32,
    timestamp_ms: u64,
) -> String                     // пустая строка — успех, иначе текст ошибки
```

Реализация: `rust/crates/ffi/src/lib.rs`, метод `ingest_audio_chunk`.

### Формат

| Что | Значение | Откуда |
|---|---|---|
| Кодирование | PCM, 16 бит со знаком, **little-endian** | `pcm_bytes_to_i16`, `rust/crates/stt/src/window.rs:167` |
| Каналов в буфере | один (моно) | сведение делает платформенный слой |
| Частота | **16 000 Гц** | `AudioChunkPipeline.targetSampleRate`, ADR-005 |
| Длина куска | **100 мс** = 1600 кадров = 3200 байт | `AudioChunkPipeline.chunkDurationMs` |

Частота передаётся параметром, но фактически ядро настроено на 16 кГц: с этой частотой работает распознавание. Приводить звук устройства к ней — задача платформенного слоя. На macOS этим занят `PCMDownmixer` поверх штатного конвертера.

### Метки времени — считать по кадрам, а не по часам

`timestamp_ms` — смещение начала куска от начала записи **этого канала**, вычисленное из счётчика кадров:

```
timestamp_ms = номер_первого_кадра * 1000 / частота
```

Системные часы для этого использовать нельзя. Причина в ADR-004: две дорожки выравниваются между собой по времени, и метка должна соответствовать самому звуку, а не моменту, когда до него дошли руки. Момент обработки плавает — на переключении устройства, на загрузке машины, на задержке планировщика, — и дорожки разъедутся.

Счётчик кадров ведётся отдельно для каждого канала и сбрасывается в начале новой записи.

### Каналы не смешивать

Микрофон и системный звук уходят в ядро **раздельно**, каждый со своим счётчиком кадров. Смешивание — не оптимизация, а потеря данных: принадлежность реплики говорящему берётся из канала (ADR-012), и восстановить её после смешивания нечем.

Ядро внутри себя сводит каналы для распознавания, но канал остаётся отдельным полем события (ADR-009). Это его дело, не ваше.

### Пропуски

Что происходит при разрыве в метках времени — например, если поток прервался на переключении устройства, — не определено. Ядро дыру не заметит и не сообщит. Если такое возможно на вашей платформе, решение надо принять явно и записать: либо не допускать разрывов, либо начинать новую сессию.

## Где лежат данные

Ядро не знает, где хранить данные, — путь ему передаёт оболочка:

```rust
MeetingCore::with_data_root(path: String)
```

Умолчание `MeetingCore::new()` кладёт данные во временный каталог (`default_data_root`, `rust/crates/ffi/src/lib.rs:332`) и годится только для тестов. Рабочая оболочка обязана передать настоящий путь.

На macOS это `~/Library/Application Support/meetingraft/`. Под Windows место надо выбрать и зафиксировать отдельным ADR — это решение, а не деталь реализации.

Внутри корня ядро само раскладывает: базу SQLite, куски звука, скачанные модели распознавания. Структура — ADR-006, схема — `rust/crates/storage/src/migrations.rs`.

## Что ещё обязана делать оболочка

- **Запрашивать разрешения** на микрофон и запись системного звука и показывать отказ человеку. Ядро о разрешениях не знает.
- **Скачивать модель распознавания** и показывать ход. Модель — больше гигабайта, без неё распознавание не запустится.
- **Показывать недоступность системного звука.** На macOS захват может не подняться, и приложение показывает это отдельным значком. Молчаливая запись одного канала — худший исход: человек проводит встречу в уверенности, что пишется всё.
